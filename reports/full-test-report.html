📚 测试事实依据

以下 15 条事实被录入 Sisyphus 记忆系统，作为 A/B 测试的知识库。A 组可检索这些记忆，B 组只能凭 LLM 训练数据回答。

① Sisyphus四层存储架构
RAW层(Markdown append-only)、REFINED层(LLM加工可重建)、MOC层(Obsidian wikilink索引)、AGENT层(子沙箱)。文件=SSOT，SQLite仅缓存。
② decay_score 记忆权重衰减
公式: importance × 0.5^(days/30)，半衰期30天。last_recalled_at优先计算时间差，为空用created_at。检索后自动更新recall_count+1和last_recalled_at。
③ SubagentLauncher 子进程调度
task.json→subprocess Python子进程→LLM+IO→result.json→主进程读。5个handler: dream/compress/recall_search/recall_relevant/classify_types。
④ ContextRetriever 三层检索
L1读INDEX.md MOC关键词重叠打分匹配类型(不依赖LLM)。L2从refined召回reflection/summary。L3从RAW按需补缺。decay_score排序截断。
⑤ MCP stdio Server
stdio JSON-RPC零依赖。4工具: write_memory/search_memory/get_context/memory_stats。兼容opencode/ClaudeDesktop/VS Code/Cursor。
⑥ AgentMemory 自动注入
before_turn(query)三条件触发全量: turn==0/store dirty/超refresh_interval。增量refined空时fallback全量。dirty由create/update/delete自动标记。
⑦ LoopDetector 回路检测
精确标题分组≥3次标记。标记最早记忆repeat_count+repeat_pattern，创建loop_record。repeat_count与recall_count语义独立。
⑧ LinkCleaner 断链清理
三种: 删除指向不存在ID的死链/移除重复链接/去除自引用。与废弃LinkAnalyzer不同: 只做清理不做自动关联。
⑨ LLM max_tokens 与 reasoning 模型
DeepSeek v4 Flash max_tokens=500时content为空(原因: reasoning_content吃光token预算)。修复: 默认2048，SISYPHUS_LLM_MAX_TOKENS可控。
⑩ 大规模测试 103 万 token
200条记忆(五大领域), Dream 4条reflection, 165次recall(58%命中率), Compress 195条。实测单次recall 5,755 token。总1,036,390 token。
⑪ Pipeline 自动流水线
5步: 回路检测→压缩→反射→MOC索引→断链清理。无LLM key时LLM步骤自动跳过不崩溃。
⑫ DreamEngine 反射机制
收集→SubagentLauncher→子进程LLM→reflection存入refined/reflection/。字段: id/title/content/importance/evidence。源记忆refined_by更新。
⑬ Compressor 退火压缩
API: run()(不是compress!)。threshold触发阈值(默认20), keep_recent保留最新N条。子进程LLM总结→创建compressed记忆→删除旧记忆。
⑭ Recall 召回机制
search(query,top_k)全记忆+query→LLM选相关ID→返回Memory列表。is_relevant(memory,query)单条评分0-1。委托recall_search/recall_relevant handler。
⑮ 188 测试覆盖全景
19文件: store/store_v2/refined/dream/compression/recall/retrieval(22条)/context(14条)/pipeline/loop/link/moc/agent/cache/log/snapshot/extraction/search/cli。全绿。

🔍 关键发现

✅ 记忆系统在特定场景下效果显著
Q9 (DeepSeek max_tokens bug) 是 A 组得分 10/10 的唯一题目。关键词恰好匹配（"DeepSeek"+"max_tokens"+"bug"）到正确的"LLM max_tokens与reasoning模型"记忆，LLM 完整复现了问题原因和修复方案。证明：当检索命中正确记忆时，系统可提供 10 倍于无记忆的回答质量。
⚠️ 简单关键词匹配不足以支撑 Sisyphus 专有知识检索
15题中 7 题 A 组得 0 分。核心原因：ContextRetriever 在无 subagent 时使用 _filter_by_keyword 做分词重叠匹配，但 Sisyphus 专有术语（"SubagentLauncher"/"LoopDetector"/"decay_score"）与问题中的自然语言 query 无法精准匹配。

根因链：中文 query 分词 → 与英文记忆标题不重叠 → 得分 0 → 关联记忆未入选 → LLM 缺少上下文 → 编造答案

解决方案：接入 LLM-powered recall（SubagentLauncher.recall_search），利用语义理解而非关键词匹配。
📈 即使不完美的检索，83% 相对提升依然存在
A 组平均 1.1 vs B 组 0.6，相对提升 83%。如果接入 LLM recall 优化检索质量，预期提升可达到 3-5x。

⭐ 最佳案例 — Q9: DeepSeek max_tokens bug (A=10, B=1)

A 组 (有记忆) — 10/10
检索命中的记忆："LLM max_tokens与reasoning模型"
使用DeepSeek reasoning模型时发现关键bug：将max_tokens设置为500会导致LLM响应content为空。原因：DeepSeek的reasoning_content字段会占用token预算，剩余给content的token不够甚至为0。修复：将默认max_tokens提高至2048，并通过SISYPHUS_LLM_MAX_TOKENS环境变量允许用户自定义。发现过程：在测试Dream反射引擎时发现返回0条reflection，排查后定位到LLM返回空字符串，分析API usage发现reasoning_tokens 21但completion_tokens 0。
B 组 (无记忆) — 1/10
使用DeepSeek reasoning模型时，需要注意其token使用量通常较大，因为模型会生成额外的推理步骤。建议适当提高max_tokens参数（如2048或更高）以避免截断。同时要监控API调用成本，因为reasoning模型通常消耗更多token。此外，确保你的API密钥有足够的额度。
分析：A 组精确复现了 bug（max_tokens=500→空content→reasoning_content占预算→2048修复），完整覆盖了发现过程。B 组只能给出通用的 token 管理建议，没有具体数字。这就是记忆系统的价值。

🚀 下一步建议

1. 接入 LLM recall 替代关键词匹配
当前 _filter_by_keyword 是简单分词重叠，不支持语义匹配。应启用 SubagentLauncher.recall_search 做 LLM 语义召回。预估可将 A/B 差距从 0.5 扩大到 3-5 分。
2. 混合检索策略
关键词快速粗筛 → LLM 语义精排的两阶段检索。第一层用 _filter_by_keyword 将候选从 200 缩小到 20，第二层用 LLM recall 从 20 中精选 top-5。兼顾速度和精度。
3. 检索质量自动监控
添加检索质量评分机制：每次检索后记录 query↔retrieved_memory 的匹配度，长期统计劣化趋势并告警。
