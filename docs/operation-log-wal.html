📋 操作日志方案

以 record-oriented log 增量重建 SQLite，替代全量 dump

既然 .md 文件是不可变的追加存储（只增不改），
那就把操作记录成 JSON 日志，SQLite 从日志回放重建，而不是从文件全量扫描。

⚙️ 怎么运作

写入路径：操作日志 + 文件 双写

1

写一条记忆 → 写 .md 文件（跟现在一样）

2

同时追加一行 JSON 到 operations.jsonl：

{"op":"create","id":"mem_xxx","type":"decision","importance":7,"ts":"2026-05-24T12:00:00","path":"mem_xxx.md"}

{"op":"update","id":"mem_xxx","field":"importance","old":7,"new":8,"ts":"2026-05-24T12:30:00"}

{"op":"delete","id":"mem_xxx","ts":"2026-05-24T13:00:00"}

每次操作就一行 JSON，append-only，不会改之前的内容。

重建路径：回放日志 → 更新 SQLite

1

进程启动时，加载 SQLite（如果存在）

2

读 operations.jsonl 的 checkpoint 标记（上次回放到哪一行）

3

回放 checkpoint 之后的全部操作 → 更新 FTS5 索引

4

SQLite 始终保持最新状态

回放速度：一行 JSON parse → 一条 SQL INSERT/UPDATE，千条耗时 <10ms。

完全恢复（从头重建）

1

SQLite 文件丢失或被删

2

从 operations.jsonl 第一行开始完整回放

3

SQLite = 所有日志回放的结果

4

验证：日志中的 id 对应 .md 文件存在

🧹 日志压缩（Checkpoint）

日志会无限增长。需要定期 checkpoint——就是 SQLite 自身的 WAL 机制：

1

操作日志积累到 N 行（比如 10000）或 M 天（比如 7 天）

2

回放全部日志到 SQLite，完成最终状态

3

截断 operations.jsonl，只保留最后一条 "snapshot" 标记

4

新的操作从这里继续 append

# checkpoint 前的日志
{"op":"snapshot","at":10000,"ts":"2026-05-24T12:00:00"}
# 新的操作从这里开始
{"op":"create","id":"mem_xxx",...}

checkpoint 后，重建速度跟日志长度无关，始终等于最后一段的操作数。

⚖️ 对比 Auto Dump

维度Auto Dump操作日志
每次操作写入量全库（340KB / 27条）✅ 1 行 JSON（~150B）
git diff⚠️ 全库噪音✅ 只有新增那行
重建速度全量 INSERT✅ 增量回放（<10ms）
时间旅行只能回到某个 commit✅ 可回放到任意操作点
审计追踪看 diff 猜✅ 精确记录每次操作
日志膨胀每次都是完整快照⚠️ 需要 checkpoint
实现复杂度加一行命令⚠️ 中等（回放器 + checkpoint）

⏳ 有趣的时间旅行能力

因为日志记录了每次操作的 old / new，你可以回放日志到任意点： 

# 回放到第 500 条操作时的状态
python replay.py --to-line 500

# 查看某个 id 的历史变更
grep "mem_6e0bb92e04b0" operations.jsonl
# → 看到它从 importance 5 → 7 → 8 的完整演变

# 回滚某个字段
# 直接找到对应行，反转 old/new 回放

这其实就是一个事件溯源（Event Sourcing）架构——状态是事件的推导结果，不是写入的瞬态。

🏗️ 完整架构三层

L1 源
.md 文件
不可变 · git 追踪
+
L2 操作日志
operations.jsonl
增量 · 可审计
=
L3 查询
SQLite FTS5
可丢弃 · 可重建

各层职责

L1 .md 文件你的审计级源数据。永远不可变，git 追踪，删了 .db 也不丢。
L2 operations.jsonl增量操作记录。append-only，每次操作 1 行 JSON，git 可追踪，时间旅行能力。
L3 SQLite FTS5只读查询索引。从 L2 回放构建，丢了从 L2 重建，不需要和 L1 实时同步。

🎯 现实检查

必要性备注
27 条记忆💤 不需要BM25 直接扫 md 文件已经 10ms
100 条🧐 可以考虑文件扫描开始感觉到延迟（~30ms）

这个方案最大的价值不是"存"，是"审计 + 时间旅行"。

即使 FTS5 你现在用不上，操作的变更记录本身就有价值——你知道每条记忆是怎么演化的，importance 从 5 变到 8 是谁改的、什么场景下改的。

但实话说：你现在 27 条记忆，先把自动触发接上，让 Pipeline 跑起来。
日志 + FTS5 是几百条以后的事。
