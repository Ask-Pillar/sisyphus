🔬 Sisyphus 重构：一切记忆都是上下文组装

2026-05-24 · 核心洞察："所有的数据对于模型来说不过是提示词和上下文罢了"

没有"记忆"这种东西，只有"上下文窗口的组装策略"。

一、七套系统，同一件事

Mem0→向量相似度→top-k→拼接→塞进 prompt
Letta→pinned blocks + 搜索→拼接→塞进 prompt
Hermes→frozen MEMORY.md→直接→塞进 prompt
Claude→MEMORY.md 索引 + 后台提取→塞进 prompt
Sisyphus→BM25 + LLM recall→<sisyphus_context>→塞进 prompt

差异只在组装规则——先装什么、装多少、什么时候刷新、装不下了怎么裁。

二、概念全部打通

传统叫法实质
PERISIST 层每 turn 无条件 prepend 固定文本，配额 ≤2000 chars
HOT 索引按时间+相关性排序，挑 top-k
Dream离线预计算"将来可能用得上的好文本"
Compress离线把旧文本压缩成更短的等效文本
Skill按触发条件动态 append 指令
代码索引函数签名/调用链翻译成文本
before_turn上述所有规则的调度器
半衰期排序分数的时间权重
冷热分层先搜小池子快，不够再搜大池子

三、简化架构

before_turn(query):
    ctx, budget = [], CONTEXT_BUDGET

    // L0 — 无条件，frozen（prefix-cacheable）
    ctx += SYSTEM_PROMPT          // 身份、工具、规则
    ctx += PERSIST.load()         // 项目上下文，≤ 2000 chars

    // L1 — 条件匹配，按优先级填充
    ctx += HOT.search(query, budget × 0.4)
    ctx += SKILL.match(query, budget × 0.2)

    // L2 — 按需，剩余配额
    if needs_code:   ctx += CODE.search(query)
    if needs_history: ctx += COLD.search(query)

    return trim_to_budget(ctx)

四个设计原则

1. 配额制，不是类型制 — PERSIST 不是"存什么"，是"占多少 token"。写太多就裁底部。

2. 排序优先级场景化 — 编码→CODE+debug；规划→决策+架构；调试→错误模式+调用链。

3. 上下文窗口就是可视化 — 显示每层占多少、裁了什么、上次组装时间。

4. Dream/Compress 就是离线预填缓存 — 提前算好下次用的好文本，省实时开销。

四、纠结直接消失

之前纠结

PERSIST 该存多少条？

热记忆和冷记忆怎么分？

Dream 什么时候触发？

为什么要可视化？

半衰期几天合适？

需要几个 MCP server？

现在消解

→ 配额说了算，存到 2000 chars

→ 同一条记忆，两个搜索池子而已

→ 配额有富余就触发，预填缓存

→ 就是看上下文窗口的占用量

→ 只是排序权重，不是强制遗忘

→ 只是上下文来源的多样性

五、实施不需要大改

现有:  before_turn() → ContextRetriever → <sisyphus_context>
改为:  before_turn() → ContextAssembler(
           sources=[PERSIST, HOT, SKILL, CODE, COLD]
       ) → ctx

ContextRetriever 变成 ContextAssembler 的一个 source。
Memory dataclass 不需要改，pinned/project/scope 是排序元数据。

六、一句话

Sisyphus 不存储记忆。它组装上下文。
Dream 是缓存预填，HOT 是快速池子，PERSIST 是永不裁切的页眉，
半衰期是时间权重——全都在做同一件事：
把最有用的文本，塞进模型前置的几千个 token 里。
