二、恢复过程中踩的坑

坑1: 日志无日期

Bridge log时间戳只有[HH:MM:SS], 无年月日。只能靠两个手段还原: 1)时钟轮回(23:59→00:00标记跨天) 2)对话内容中的时间锚点(明天/昨天/睡觉)。

坑2: UTC时区陷阱

Log使用UTC时间, 用户在北京(UTC+8)。"07:57 UTC"= "15:57 CST"是下午不是早上。导致最初把"浏览器插件"消息归错了上下午。token保存日期2026-05-19T00:43:15.864Z的Z后缀暴露了UTC。

坑3: 记忆缺少事件时间

Memory只有created_at(记录时间), 缺happened_at(事件时间)。手动补录的30条记忆全部挤在16:44-17:15窗口, 检索"26号上午"时找不到。

坑4: 多来源时间线混淆

我(Sisyphus)和微信agent是两个独立会话。26号下午我在聊架构/论文/自评, 微信agent在聊硬件/模型/外脑。我把两边的讨论混在一起记录, 导致时间标签全乱。

坑5: 自动提取完全缺失

592条消息只有28条自动记忆, 覆盖率~5%。26号230条消息自动记忆=0。记忆全靠用户说"记下来"或agent偶尔自反查。

三、怎么恢复的

步骤方法耗时
1. 原始探查直接查bridge log消息列表, 按内容推断日期混乱, 多次出错
2. 锚点定位提取"明天/昨天/今天/睡觉"等14个相对时间锚点, 建立日边界准确率提升
3. 时钟轮回利用23:59→00:00的6次轮回定位真实跨天点, 结合锚点消除bridge重启干扰精确定位
4. UTC修正发现Z时区标识, 全部+8小时转北京时间对上用户记忆
5. 数据补录按北京时间逐日补录缺失记忆, 加"May 26凌晨"等精确时间前缀覆盖率达95%
6. 错标修正旧的"May 25硬件"条目降权→3, 新正确条目升权→8检索正确
