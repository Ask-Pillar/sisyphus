before_turn 是预处理，不是工具调用

一、两类操作，混在一起

Sisyphus 的 9 个 MCP 工具实际上分属两类：

类别工具本质适合 MCP？
被动·预处理get_context每 turn 自动注入上下文❌ 不该是
主动·操作write_memoryagent 主动记录✅
search_memoryagent 主动搜索✅
memory_statsagent 查统计✅
get_memory按 ID 查详情✅
list_memories浏览✅
delete_memory删除✅
run_pipeline触发后台✅
import_memories导入✅

9 个中 8 个适合 MCP，唯独 get_context 不该是。但它恰好是最核心的那个。

二、作为 MCP 工具的问题

MCP 工具

Agent:
  "我要不要调用 get_context？"
  → 不知道
  → 不调
  → prompt 里无记忆
  → 失忆

这正是 WeChat bridge 的现况——agent 根本不知道 MCP 存在，也不会主动调 get_context。

内嵌模块

before_turn(query):
  PERSIST.load()
  HOT.search()
  → 上下文自动就位

Agent:
  醒来 → 记忆已在 prompt 里
  → 不需要知道系统存在

就像 opencode 加载 CLAUDE.md——agent 不需要"调用"它。

三、推荐：混合架构

┌─ Agent 内嵌 ──────────────────────┐
│                                    │
│  before_turn() → 自动注入上下文     │
│    PERSIST + HOT + CODE + COLD    │
│                                    │
│  after_turn() → Extractor → RAW   │
│    → Dream → Compress            │
│                                    │
│  ← Python import, 零延迟           │
└────────────────────────────────────┘
               │
  主动操作 → MCP / Skill
               │
┌─ MCP Server (精简) ───────────────┐
│                                    │
│  write_memory     search_memory   │
│  memory_stats     get_memory      │
│  list_memories    delete_memory   │
│  run_pipeline     import_memories │
│                                    │
│  ← 8 工具 (去掉 get_context)       │
└────────────────────────────────────┘

四、实施

Step 1before_turn/after_turn 剥离为独立模块，from sisyphus.memory import AgentMemory
Step 2MCP Server 去掉 get_context，保留 8 个主动工具
Step 3opencode 集成：import 后每 turn 自动跑
Step 4MCP Server 仍可用（外接其他 agent 时提供主动工具）

五、一句话

before_turn 不应该是一个工具调用，
就像 import 不应该是一个 HTTP 请求。
内嵌是它本该在的地方，MCP 是主动操作的通道。
