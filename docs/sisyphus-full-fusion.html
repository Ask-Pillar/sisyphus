🧠 Sisyphus 三层存储 × 全维度融合方案

把记忆类型 · 耐久分区 · 作用域全部嵌入三层架构，一次设计到位

一、现状：三种维度属于不同切片

你之前设计的三种维度不是平替关系，是从不同角度标注同一条记忆：

维度含义枚举值用在哪儿
类型 语义分类 — "这条记忆是什么" decision lesson pattern project_context user_preference note reflection compressed 检索过滤、可视化着色、Dream 优先级
分区 耐久策略 — "这条记忆能活多久" PERSIST HOT CODE COLD 每次 turn 的注入策略（必加载/优先/按需/衰减）
作用域 归属范围 — "这条记忆属于谁" global project session 跨项目隔离、session 自动清理
关键设计：这三者是正交的。一条记忆可以是 decision PERSIST global（全局架构决策），也可以是 note HOT project（当前项目的临时笔记）。

二、三层架构不改变任何维度，只是换了底层引擎

# 无论存成什么引擎，这三种维度都是 `Memory` 对象本身的属性 # 当前（纯文件） Memory { id, type, title, content, tags[], importance, created_at, last_recalled_at, status ← 现有 pinned, scope, project ← 已设计未实现 } ↓ 读写 .md 文件 ↓ 检索: 扫全量 → 内存 BM25 → 按衰减排序 # 融合 SQLite 后（三层架构） Memory { ← 字段不变！还是同一组字段 id, type, title, content, tags[], importance, created_at, last_recalled_at, status, pinned, scope, project ← 照样在这里 } ↓ 写: .md (L1) → operations.jsonl (L2) → SQLite index.db (L3) ↓ 检索: SQL 查询 index.db → FTS5 + 任意维度过滤 → 按衰减排序

变化不在于"有什么字段"，而在于"怎么查更快"。类型/分区/作用域这些字段在 SQLite 里就是 column，可以自由组合查询。

三、SQLite schema：一个字段都不落

-- memories 表（主表） CREATE TABLE memories ( id TEXT PRIMARY KEY, -- mem_xxx type TEXT NOT NULL, -- lesson|decision|pattern|project_context|... title TEXT NOT NULL, content TEXT NOT NULL, tags TEXT NOT NULL DEFAULT '[]', -- JSON array importance INTEGER NOT NULL DEFAULT 5, -- 1-10 created_at TEXT NOT NULL, -- ISO 8601 last_recalled_at TEXT, -- ISO 8601 status TEXT NOT NULL DEFAULT 'active', -- active|archived|deleted -- 你之前设计的三个维度 👇 pinned INTEGER NOT NULL DEFAULT 0, -- 0/1，PERSIST 层标记 scope TEXT NOT NULL DEFAULT 'global', -- global|project|session project TEXT NOT NULL DEFAULT '' -- 项目名称（scope=project 时使用） ); -- FTS5 全文索引 CREATE VIRTUAL TABLE memories_fts USING fts5( title, content, tags, content='memories', content_rowid='rowid', tokenize='unicode61 token_chars ""' -- 中文走 unicode61 + jieba 预处理 ); -- 向量列（预留，Phase 2） -- sqlite-vec 用 VECTOR 列，等生态成熟再补 -- 操作日志（L2） -- type: create|update|delete|checkpoint CREATE TABLE operations ( seq INTEGER PRIMARY KEY AUTOINCREMENT, ts TEXT NOT NULL, -- ISO 8601 type TEXT NOT NULL, -- create|update|delete|checkpoint mem_id TEXT, payload TEXT -- JSON, 变更前的完整 Memory 快照（delete 时保留） );
结论：类型（type）、分区（pinned）、作用域（scope/project），一个字段都没丢。它们从 .md 文件的 frontmatter 变成了 index.db 的 column，语义不变，查询更快。

四、分区在 SQLite 中的查询映射

分区入选条件在 SQLite 中的查询
PERSIST pinned=1 或 importance≥8 且 type in (project_context,decision,pattern) 
SELECT * FROM memories
WHERE status='active'
  AND (pinned=1 OR (importance>=8 AND type IN ('project_context','decision','pattern')))
ORDER BY importance DESC;
HOT 7 天内创建的活跃记忆（排除 PERSIST） 
SELECT *, importance * POW(0.5, JULIANDAY('now')-JULIANDAY(created_at)/180.0) AS score
FROM memories_fts
WHERE memories_fts MATCH ?
  AND status='active' AND pinned=0
  AND created_at >= date('now','-7 days')
ORDER BY score DESC;
COLD 其余活跃记忆（FTS5 全文检索 + 衰减排序） 
SELECT *, importance * POW(0.5, JULIANDAY('now')-JULIANDAY(created_at)/180.0) AS score
FROM memories_fts
WHERE memories_fts MATCH ?
  AND status='active' AND pinned=0
  AND created_at < date('now','-7 days')
ORDER BY score DESC;
CODE 独立索引（CodeGraphContext 图数据库，不走 SQLite）

精妙之处：纯文件时代分区是靠"读哪个文件"来实现（PERSIST.md vs HOT.md vs INDEX.md），SQLite 时代靠"查询条件"来实现。后者灵活得多——你随时可以加新的分区策略，不涉及文件拆分。

五、类型和分区怎么组合检索

SQLite 可以同时用 type + pinned + scope 做任意维度过滤：

场景SQL 查询
"当前项目有哪些架构决策" 
SELECT * FROM memories
WHERE type='decision' AND status='active' AND project='disk-demo'
ORDER BY importance DESC;
"所有 PERSIST 层的 lessons" 
SELECT * FROM memories
WHERE type='lesson' AND status='active'
  AND (pinned=1 OR (importance>=8))
ORDER BY created_at DESC;
"全局的 project_context（跨项目）" 
SELECT * FROM memories
WHERE type='project_context' AND scope='global' AND status='active';
"本 session 刚记的笔记" 
SELECT * FROM memories
WHERE scope='session' AND status='active'
  AND created_at >= datetime('now','-24 hours')
ORDER BY created_at DESC;
"全文检索 + 排除 session 临时数据" 
SELECT *, importance * POW(0.5, ...) AS score
FROM memories_fts WHERE memories_fts MATCH ?
  AND status='active' AND scope != 'session'
ORDER BY score DESC;

六、before_turn 注入流程（三层架构版）

def before_turn(query: str, project: str) -> str: # 第一步：PERSIST 层 — 无条件注入，不占配额 persist = db.execute(""" SELECT * FROM memories WHERE status='active' AND (pinned=1 OR (importance>=8 AND type IN ('project_context','decision','pattern'))) ORDER BY importance DESC """) # 第二步：HOT 层 — 7天内优先 hot = db.execute(""" SELECT *, importance*POW(0.5, ...) AS score FROM memories_fts WHERE memories_fts MATCH ? AND status='active' AND pinned=0 AND created_at >= date('now','-7 days') ORDER BY score DESC LIMIT ? """, [query, top_k - len(persist)]) # 第三步：COLD 层 — fallback 全文检索 cold = db.execute(""" SELECT *, importance*POW(0.5, ...) AS score FROM memories_fts WHERE memories_fts MATCH ? AND status='active' AND pinned=0 AND created_at < date('now','-7 days') ORDER BY score DESC LIMIT ? """, [query, top_k - len(persist) - len(hot)]) # 合并 → 格式化为 <sisyphus_context> return format_context(persist + hot + cold)

八、总结：三层架构没有丢掉任何你已有的设计

┌─ 类型 (type) ─────────────────────────────┐ │ lesson · decision · pattern · project_context │ Memory 对象 │ user_preference · note · reflection · compressed │ ────────── ├─ 分区 (pinned) ───────────────────────────┤ id │ PERSIST · HOT · COLD · (CODE 独立) │ type ├─ 作用域 (scope + project) ────────────────┤ title │ global · project:"sisyphus" · session │ content └──────────────────────────────────────────┘ importance ↓ ↓ ↓ created_at 全部存入 SQLite column pinned ──→ WHERE 任意组合查询 scope project ┌─── 三层引擎 ─────────────────┐ │ L1 .md (git 追踪，不可变) │ │ L2 .jsonl (操作日志，审计) │ │ L3 SQLite (index.db，FTS5) │ └──────────────────────────────┘

一句话结论：类型是"这条记忆讲什么"，分区是"这条记忆存多久"，作用域是"这条记忆属于谁"——三个轴互不冲突。SQLite 只是让三个轴都能被同一个引擎高效检索，而不是各自靠不同的文件/索引去实现。
